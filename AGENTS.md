# LauncherKit Guidelines

This repository is LauncherKit, the reusable core of Skyrim SE / Mod Organizer modpack launchers. Consumers include it as a Git submodule at `kit/` and reference its projects, MSBuild props and installer by path; see [README.md](README.md) for consumer setup. The reference consumer is STB Launcher (the Skyrim True Believer launcher, STB below): STB names in these rules are examples of consumer-owned code, never kit dependencies. Consumer repositories own their views, branding, mock archives, deployment and release policy.

Paths below are relative to this repository; commands run from its root unless stated otherwise. Commands that need a launcher executable (NUKE targets, sandbox, AOT publish) run from a consumer repository root, where this repository is `kit/`. The kit must build and test without consumer props, generated identity, projects or fixture state.

## Architecture and ownership

- `src/LauncherKit.Infrastructure` owns shared filesystem/logging primitives; `Core` owns Skyrim SE/Mod Organizer domain behavior, feed/update selection, tasks, storage, persistence, FOMOD and account integrations.
- `src/LauncherKit.Desktop` owns Avalonia-free view models, typed presentation facts, activation, localization and `IUiDispatcher`; it has no Avalonia, FluentAvalonia or R3Extensions.Avalonia reference.
- `src/LauncherKit.Desktop.Avalonia` owns Avalonia converters, controls, the AOT-safe view registry/locator, UI dispatcher, platform services, taskbar integration and application host. It has no FluentAvalonia dependency and supplies no default views or consumer design data; navigation frameworks, themes and frame page factories belong to consumers.
- `LauncherKitApp` is the abstract Avalonia application host. It seals startup and owns logging, configuration, kit registrations, the application scope, localization, installing the DI-resolved locator, scope reloads, exception logging and disposal. Consumers provide product identity, `BeforeConfiguration`, `GetInMemoryConfiguration`, `ConfigureServices`, `OnServicesBuilt`, `LoadXaml`, `ReloadViews` and optional `StartDesktopServices`. In-memory settings precede JSON and environment overrides. `LoadXaml` must call `AvaloniaXamlLoader.Load(this)` in the consumer's `x:Class`, so Avalonia binds precompiled XAML correctly. `LauncherKitProgram` owns entry-point and designer configuration.
- `BeforeConfiguration(LauncherProductOptions)` receives no logging factory or services. Pre-configuration dependencies are consumer-owned: STB creates and disposes a temporary `SerilogLoggerFactory` over the configured `Log.Logger` with `dispose: false` for its legacy-directory migration, leaving the shared logger alive.
- The kit defines the memberless abstract `MainWindowViewModelBase`. Consumers register a scoped implementation under that base type. `LauncherKitApp` only resolves it as the main window's data context at startup and after scope reloads; a missing registration fails through `GetRequiredService`. All main window state and logic belong to the consumer. STB owns its concrete `MainWindowViewModel`, including `HomePage`, setup-versus-home selection, navigation pages and collect-logs command. Setup behavior and individual page services remain in the kit; there is no wrapper shell model.
- Consumers register their window as a singleton under the memberless `IMainView` interface. The kit resolves it with `GetRequiredService<IMainView>()` at startup and requires it to be an Avalonia `Window`, throwing an explicit `InvalidOperationException` otherwise. Consumers choose any window base class deriving from `Window`. There is no `GetMainWindow` hook or default window registration. Main-model page construction and setup gating are consumer-owned; neither main-model factory type remains in the kit.
- `AddLauncherKitDesktop` registers `ViewLocator` as a singleton. It resolves the consumer's `IViewRegistry`, fails startup naming it when missing, and builds views with the current scope's services (`LauncherKitDesktopOptions.GetCurrentServices`). `IViewRegistry` has only `CreateView(ViewModelBase, IServiceProvider)`. Consumers implement their mapping, throwing for unknown models. The locator is the first application data template and rejects data that is not a `ViewModelBase`; consumers adapt their navigation controls to it. STB registers its own `FramePageFactory` and adds its `FAFrame` application style after loading its XAML.
- `src/LauncherKit.LogsCollector.Core` is a sidecar library; consumers own the executable entry point and console texts. `LogsCollectorRunner.Run(createRootDirectoryManager, errorMessage, completionPrompt, cancellationToken)` owns console-host composition, standard launcher/MO/SKSE sources, collection into the current directory, error reporting and the final key wait. Consumers supply their registry-reading root directory manager (from the runner's `IFileSystemUtils` and `IRegistryManager`), an exception-to-text callback and the completion prompt. `LauncherLogsSource` skips launcher files with a warning when the root is not registered, so the other sources still run.
- `LaunchersRootDirectoryManager` is abstract and consumer-implemented; the kit registers no `ILaunchersRootDirectoryManager`, so consumers register theirs. With `useCurrentDirectory` (the launcher itself) the root is the consumer's `RootFromCurrentDirectory(IFileSystemUtils.GetCurrentDirectory())`, so development, sandbox and copied launchers never use an installed root; otherwise (the log collector) it is the `LaunchersRoot` registry value (`LaunchersRootDirectoryManager.RootRegistryValueName`) that the consumer's installer writes under `LauncherProductOptions.RegistryKey`, and a missing value throws `InvalidOperationException`. The root is resolved and created on first access. `TryGetInstalledLauncherDirectory` locates the installed launcher by the consumer's installation layout. `IRegistryManager`/`RegistryManager` live in Infrastructure.
- `msbuild/LauncherKit.Product.props` and `src/LauncherKit.ProductIdentity.Generator` turn a consumer's product props into code. The consumer's single product props file sets the `Launcher*` properties and `VersionPrefix`, then imports `LauncherKit.Product.props`. In every C# project importing the consumer props, the generator (an analyzer `ProjectReference`; netstandard2.0, `TreatAsLocalProperty="PublishAot"` because the launcher's AOT publish sets it globally) emits `$(LauncherProductNamespace).ProductIdentity` with one constant per value and `CreateOptions()`. A missing or blank property fails the build with `LKPI001`. `ProductIdentityGenerator.OptionNames` and the props' `CompilerVisibleProperty` list must stay in sync.
- `installer/` is the launcher installer, built from the same consumer props.
  - `LauncherKit.Installer.props` turns a `WixToolset.Sdk` project into the per-user MSI of `Package.wxs`. The package installs the publish output (`LauncherPublishDirectory`) into `LAUNCHERDIR` and writes `Installed`, the shortcut choices and `LaunchersRoot` (`LAUNCHERSROOT`) under the registry key. It also adds the optional shortcuts, `RemoveAllData` (`RemoveFolderEx` of the root and the registered data folders), closing a running launcher and starting it after install.
  - The location is the consumer's layout, not kit policy. The importing project's own `.wxs` defines the `LAUNCHERSROOT` and `LAUNCHERDIR` directories and may add components to the `Launcher` feature through `FeatureRef`. Every consumer therefore has a package project.
  - Optional folder choice: a consumer setting `LauncherInstallerDefaultFolder` (a Burn/MSI formatted path, e.g. `[LocalAppDataFolder]Programs\MyLauncher`, equal to its layout's default `LAUNCHERSROOT`) gets `LauncherInstallerFolderChoice=yes`; without it (STB) both projects build exactly the fixed-root setup, with `SuppressOptionsUI`. With it, the bundle shows the Options button and folder page (`InstallFolder`, overridable on the command line) and passes `LAUNCHERSROOT=[InstallFolder]`. Once installed, `InstallFolder` is the registered `LaunchersRoot` and the theme hides the Options button, so upgrades never move the root. The MSI records whether `LAUNCHERSROOT` was passed before costing (`SetDirectory` runs after `CostFinalize`) and otherwise stays in the installed root. Because the root may hold other files, `RemoveAllData` removes only the registered `LauncherDirectory` and `ToolsDirectory` (`RemoveFolderEx`) and `launcher.db*`, then the root if it is empty, instead of the whole root.
  - `installer/Bundle/LauncherKit.Installer.Bundle.wixproj` is the per-user Burn setup (`Theme.xml` adds the shortcut and `RemoveAllData` checkboxes to WiX 7.0.1's `HyperlinkTheme.xml`; `Theme.ru-ru.wxl` is Russian, and the `RemoveAllData` text shows the registered `LaunchersRoot`). It chains the consumer's required `LauncherInstallerProject` through a `ProjectReference` named `LauncherInstaller`. Its version is `VersionPrefix[-VersionSuffix]`; Burn refuses older bundles (1638), which matches `UpdateProvider` offering only newer launchers. Upgrade codes come from `LauncherInstallerPackageId`/`LauncherInstallerBundleId`; product codes are new on every build, and the MSI's `MajorUpgrade AllowDowngrades` also replaces a same-version package (a prerelease and its release share the numeric MSI version).
  - `LauncherKit.Installer.Shared.props` checks the shared properties and passes them to WiX as `$(var.<Name>)`. It rejects a `LauncherRegistryKey` outside `HKEY_CURRENT_USER\` (WiX gets its path as `LauncherRegistryKeyPath`) and values containing `;`.
  - Required installer properties are `LauncherManufacturer`, `LauncherInstallerPackageId`/`LauncherInstallerBundleId` (WiX derives the upgrade codes from them, so they are persisted identity), `LauncherInstallerOutputName`, `LauncherIconFile`, `LauncherInstallerLogoFile` and `LauncherInstallerProject`, plus the shared `LauncherDisplayName`, `LauncherAppExecutableName` and `LauncherRegistryKey`.
- The launcher side of the installer contract: `DataDirectoriesRegistrationInitializer` writes the data directories (`DownloadsDirectory`, `TempDataDirectory`, `AppDataDirectory` unless a drive root) under `LauncherProductOptions.RegistryKey` on start and on settings changes, for the data-removal option; the log collector reads `LaunchersRoot`; `AppTaskProvider.CreateUpdateLauncherTask` starts the downloaded setup unelevated with `/passive` (a Burn argument), then exits.
- `src/LauncherKit.DevAutomation` is development-only. See [dev automation](docs/dev-automation.md); production publish must explicitly disable it. `src/LauncherKit.ConsoleHelper` is a developer console tool (beta code hash, file SHA-256, test download with its own developer identity; the feed comes from `LAUNCHER_DOWNLOAD_HELPER_Feed__FeedPath` and `..._Urls__Feed__MainUrl`/`ProxyUrl`).
- `src/LauncherKit.FeedEditor` is the independently runnable Blazor Server/MudBlazor editor. It has no production project reference to Core; its tests compare the JSON contracts. Its `Dockerfile` builds from a consumer repository root (it copies the consumer's `global.json` and `kit/` paths), where the consumer's `compose.yaml` and `.dockerignore` select the context.
- `src/LauncherKit.Build` provides reusable NUKE components targeting `net10.0`; consumers supply project/executable names and their product props, and own release policy.
- `fomod-installer/` has its own build configuration and fixture corpus. `workers/analytics/` owns reusable Worker code and independent test configuration, not consumer routes/datasets.
- `scripts/launcher_dev.py`, `launcher_client.py` and `feed_editor_dev.py` are standard-library Python development tools; consumer flow scripts and mock archives stay outside the kit.

## Required consumer identity

`LauncherProductOptions` is an input contract, never a source of default identity. Consumers must explicitly provide every required directory, local database filename, OAuth entropy, environment prefix, executable/display/User-Agent name, Mod Organizer directory/profile, modpack version-file path, user-mods separator and installer registry key. The global database in the launchers root is always `LauncherConstants.GlobalDatabaseFileName` (`launcher.db`). Missing identity must fail during composition before resolving prefixed configuration or accessing filesystem/database/token state. Never use STB values, `LauncherKit`, names derived from the display name, or other fallback identities.

Product options use init-only properties. Required identity strings must be supplied in the object initializer (`required`); keep runtime validation for blank strings. Product-specific help links belong in consumer localization (`<consumer>.Localization.LauncherKit.DesktopStrings` overrides), not in product options or configuration.

Starting programs is consumer-defined: `HomeViewModel.StartGameCommand` and `IAppTaskProvider.CreateRunGameTask` take a `GameLaunch(Name, SkyrimRelativePath? ProgramPath)` and start the program through Mod Organizer (a `null` path opens Mod Organizer itself) after installing the newest offered modpack. `AppTaskDescription.RunGame(Name, ProgramPath)` and `MicroTaskDescription.GameStarted(Name)` render the consumer's name as is. The kit has no game variants; STB's live in its `StartGameVariant`.


`LauncherKit.Build.LauncherBuild : NukeBuild` is the reusable build host base. A consumer derives its `Build`, supplies `LauncherProjectName`, `CollectorProjectName`, `CollectorExecutableName`, `FeedEditorProjectName` and `ProductPropsFile` (its product props, whose `VersionPrefix` and `LauncherInstallerOutputName` must be literals: the build reads them as XML), and selects defaults in `Main`. `KitDirectory` defaults to the consumer's `kit/` submodule. Executable names omit the extension. Inherited targets are `Clean`, `Test`, `PublishLauncher`, `CleanLauncherSymbols`, `PublishInstaller` (builds `installer/Bundle` with `LauncherProductProps`/`LauncherPublishDirectory`, non-incrementally because WiX's up-to-date check misses a changed publish output, and copies `{name}.msi`/`{name}.exe` to `out/{name}_{version}.*`), `PublishConsoleCollector`, `PublishConsoleHelper` (the kit's `LauncherKit.ConsoleHelper`) and `PublishFeedEditor`; project and product names have no kit fallback.

`LogsCollector` receives `IEnumerable<ILogsSource>`; `ILogsSource.GetFiles(string? modOrganizerDirectory, ILogger)` returns `LogFile(FilePath, EntryName)` entries. `LauncherLogsSource`, `ModOrganizerLogsSource` and `SkseLogsSource` are registered with `TryAddEnumerable`; consumers add their own sources through DI and own console wording. Source implementations and collector path inputs must not discover consumer assembly identity.
Consumer executable assemblies get their identity only from the kit generator over their own product props; runtime kit assemblies must neither import those props nor discover identity by reflection. The console collector runner receives explicit product identity; custom collection hosts can supply paths and sources directly to `LogsCollector`. Persisted names/entropy are compatibility contracts: changes require an intentional migration, not a rename. Kit tests supply complete independent fixture identities.

## Desktop contract

1. View models do not inject dialog, markdown, notification or directory-picker services. Consumers choose wording, icons, confirmations and UI surfaces in their views.
2. Commands act directly. Confirmation belongs to the view; collected input is a command parameter (`DeleteOldSavesCommand(int keepCount)`, `InstallModpackVersionCommand(AvailableModpackVersion)`).
3. Expose facts, not consumer texts: `RequiresNewGame`, typed unavailable/validation/result values, Discord membership and download deletion outcomes. `DesktopStrings` supplies default localized texts for typed facts through kit converters; consumer resources may override branding.
4. Outcomes that outlive command waiting are R3 observables, including `OldSavesDeleted` and delayed `FeedLoadStatus`. Pending launcher/modpack changelogs and their mark-shown methods belong to view models; views only display them.
5. Keep business logic, task choice view-model creation, choice-step state and close coordination out of views. The close coordinator uses neutral `AppCloseContext`; the consumer implements confirmation and waiting for `TaskCount == 0`.
6. Marshal through injected `IUiDispatcher`/`ObserveOnUi(dispatcher)`, never Avalonia's dispatcher from `Desktop`. Tests use an immediate dispatcher unless platform behavior itself is under test.
7. No design constructors/instances or fixed consumer page set in kit view models. Consumers compose their shell and design data around the kit's page view models and `FirstSetupViewModel.IsRequired`. `SettingsViewModel.DiscordIntegration` is null when Discord is not configured.
8. First setup is a router over steps (`ViewModels/Setup/`). Each scoped `ISetupStepProvider` (registered with `TryAddEnumerable`) returns the `SetupStepViewModel`s the current settings still need from `CreateSteps(FirstSetupContext)`. `FirstSetupSteps.Create` orders providers by `Order` (stable; kit values in `SetupStepOrder`: language 50, Skyrim directory 100, data directory 200, availability 1000) and concatenates their steps. The kit's `FirstSetupViewModel` registration passes that list and the shared `FirstSetupContext` to the model.
   - The setup is required only when the list is non-empty. The kit providers offer the language step until `App:Language` is a supported language (`LanguageCulture.IsSupported`: `en` or `ru`; there is no operating-system choice), the Skyrim/data directory steps while their setting is empty, and the availability check while the singleton `AvailabilityCheckState.IsRequired`: until a check has succeeded, which the step stores at once as `AvailabilityCheckState.CheckSucceededKey` (`FeedAvailabilityCheckSucceeded`) in the global key-value storage. The check alone therefore requires setup, also for installations configured before the key existed. Continuing without downloads stores nothing and skips the check only for the rest of the run (otherwise the setup's configuration reload would require it again at once); the next start offers it again. A consumer that fixes `App:Language` in its configuration never gets the language step.
   - `LanguageSetupStepViewModel` offers `LanguageCulture.Languages` (`en`, `ru`: the kit's translations), preselects the operating system's language when supported (otherwise English), and on next stores the choice, applies its culture and reloads views (`AppReloadMode.Language`), so the remaining steps are shown in it. Until a language is chosen the operating system's UI culture is used. `SettingsViewModel` cannot save without a supported language.
   - A step owns its validation and its edits to `FirstSetupContext.Settings`, then calls `GoNext`/`GoBack`. The router supplies those callbacks while the step is shown and clears them when hiding it (`IsShown`, `CanGoBack`, `BackCommand`), so only the current step can move the setup. Going past the last step saves the settings and reloads the configuration.
   - `OnShown` re-reads settings applied by earlier steps (directory conflicts). Welcome or intro pages are consumer views, not steps.

## Task queue, installation, feed and storage contracts

The following describe reusable behavior. Mentions of views (`HomeView`, `GraphPacksView`, `ModCardView`, `AppTaskView`, the Downloads page) describe how the reference consumer renders facts, not dependencies from the kit onto views. Physical identity paths come exclusively from product options.

- `LauncherKit.Core` owns launcher behavior: feeds and update selection, download/storage, task orchestration, Mod Organizer integration, archive extraction, FOMOD installation, and persistence. Keep business logic here rather than in views.
- `LauncherKit.Infrastructure` contains shared filesystem/logging helpers. The log-collector library is a separate sidecar hosted by a consumer executable.
- Typical UI flow: a view model creates a task graph through `AppTaskProvider` or `InstallAppTaskProvider` -> `AppTaskQueue` executes dependency-aware microtasks -> R3 events/progress update UI view models. `AppTaskQueue.Enqueue` queues incomplete dependencies depth-first in their listed order, so a task's first dependency and everything it depends on run before its later dependencies. Removing a queued task (`CancelAppTask`) also removes the queued tasks depending on it and the queued dependencies that were not enqueued on their own and that no remaining task needs. After each successful task the queue checks every queued task's `AppTask.IsUnneeded`; a task reporting `true` is skipped, not cancelled: it leaves the visible queue at once (`TaskRemoved`), but stays hidden in the queue and completes without running only when it reaches the front, so its dependents still wait for its dependencies and cancelling one of those still removes them.
- `IAppTaskQueue.TaskCount` (with `INotifyPropertyChanged`) is the number of visible tasks: the running one, failed ones awaiting resume/cancel, and queued ones not skipped as unneeded. It is updated and notified under the queue lock, on the queue's thread, so subscribers must marshal to the UI thread. Consumer close confirmation may subscribe only while open, closing and allowing the close once the count reaches zero.
- Typical install flow: `FeedProvider` -> `FileSourceDownloader` -> `FileStorageService` -> `SevenZipService`/`FomodInstaller` -> `ModOrganizerService`.
- A mod version's archive (`ModFeedItem.ArchiveDownloadInfo`) and every feed `installMod` action are downloaded and then installed by `InstallModMicroTask`: an archive with a root `FOMOD/ModuleConfig.xml` (detected by `IFomodInstallService.IsFomodArchive`) is configured by the user and installed through `FomodInstaller`; any other archive is extracted whole by `ModOrganizerService.InstallMod`. Both activate the mod and its plugins in the selected profile.
- An `AppTask`'s microtasks provider gets a `MicroTasksProviderContext` built by `AppTaskQueue` in the scope the task runs in: its `MicroTasksFactory` and its `ServiceProvider`, from which a provider resolves other scoped microtask builders. Feed `InstallStep`s and their `InstallAction`s become microtasks only through `IInstallStepsMicroTasksFactory` (`AppTasks/InstallSteps/`, scoped, with `IMicroTasksFactory` injected), resolved from that `ServiceProvider`; every feed-driven installation (optional mods, graph packs, modpacks and their patches) reuses it instead of mapping actions itself. `CreateInstallMicroTasks` runs a step list in order (conditions and `selectRequiredMod` results are scoped to that list, so a condition's `StepIndex` refers to the same list) and `CreateRollbackMicroTasks` undoes its `CanRollback` steps. Callers add what is specific to them: `InstallAppTaskProvider` downloads and installs the mod's own archive with `IMicroTasksFactory` before the steps, removes the mod itself after the rollback, and writes `meta.ini`. A new action is added to `InstallAction` and handled in this factory (install and rollback switches), not in the callers. `removeFileSystemItem` deletes its `Paths` (files or directories relative to the Skyrim directory, in order, skipping missing ones) in one microtask; with the optional `FailOnFailedDelete` (`true` when missing, the editor's "Прерывать установку, если не удалось удалить") it fails on the first path it cannot delete, otherwise such a path is skipped.
- Rollback of `removeFileSystemItem`, `extractArchive` and `mergePlugins` uses backups (`Core/Backups/`): `CreateInstallMicroTasks` takes an `InstallBackupId` (`null` for steps never rolled back, i.e. modpack patches, which then delete and overwrite without backups), and `CreateRollbackMicroTasks` the same ID. `InstallAppTaskProvider` passes `InstallBackupId.ForModVersion(mod, version)` for a mod version's steps and for each patch's steps. Only `CanRollback` steps take backups. `IInstallBackupService` (scoped) keeps them in `<Skyrim>\<SkyrimDataDirectoryName>\Backups\<id>\<step>.<action>\`, on the Skyrim volume, so files are moved rather than copied: `removeFileSystemItem` moves each path into `Files\` (file by file, subdirectories recreated) instead of deleting it; `extractArchive` runs a microtask before the extraction that lists the archive (`ISevenZipService.ListArchiveEntries`), moves every file it would overwrite into `Files\`, and writes `Created.txt` (Skyrim-relative paths of the files and directories, the latter ending with `\`, that do not exist yet); `mergePlugins` keeps the profile's `plugins.txt` before the merge, the merged file and the profile name (`PluginsMergeBackup`, in `Plugins\`, the profile written last as the completion marker). All of its file system access goes through `IFileSystemUtils`, which was extended for it (existence checks, recursive listing, line reads/writes); a failed `SafeDelete*` is rethrown. A file that already has a backup keeps it (the file in its place came from an earlier run of the same action), and `Created.txt` is written before anything is extracted, so a failed or resumed task (which rebuilds and reruns all its microtasks) can repeat the actions. Rolling an action back (`Restore`) deletes its created files, moves the backed up files back over whatever is in their place, deletes the created directories left empty, then deletes the action's backup; an action without a backup (skipped by its condition, or installed by a launcher without backups) is skipped with a warning. Uninstalling or updating a mod deletes all its backups (`InstallBackupId.ForMod`) after removing the mod, and installing a mod that is not installed deletes its stale backups first (e.g. its directory deleted by the user), since restoring them could bring back outdated files. Installing a mod version (not a patch-only update) marks it unfinished (`StartInstallation`: an empty `Installing` file in the version's backup directory) right before the mod archive is installed, and `FinishInstallation` removes the mark once `meta.ini` has the version. Until then the mod directory does not tell which version it holds (its `meta.ini` is missing or the archive's own), so `InstallAppTaskProvider` takes a marked version as the installed one: a resumed or repeated installation rolls back that version's steps from their backups and reinstalls it (never only its patches), and uninstalling rolls it back too. Deleting the mod's backups deletes the mark. Uninstalling modpack and installing modpack (first installation, reinstallation, major update) delete the whole backups directory (`DeleteAll`) right after deleting the Mod Organizer directory, since none of the mods the backups belong to is left; patches keep it.
- The rollback undoes only the actions that ran. The actions that leave no backup (`installMod`, `activateMods`, `activatePlugins`, `changeProfile`) are recorded in `<LocalDatabaseFileName>` through `IInstallBackupService` (`SkyrimLocalDbContext`): `TrackedInstallations` holds each `InstallBackupId.RelativePath` whose actions are recorded, added by `StartInstallation` (before the `Installing` mark, so an unfinished installation is always tracked) and by `CreateInstallMicroTasks` before a step list with any `CanRollback` step (for patches), and `AppliedInstallActions` holds the ID, step and action index of each such action of a `CanRollback` step, inserted right before the action runs and inside its step's condition, so an action skipped by its condition or never reached by an interrupted installation has no record, while one interrupted halfway has one. Rolling such an action back runs only when its ID is tracked and the action is recorded, then deletes the record (`Delete(InstallActionBackup)`), so a repeated rollback skips it; an untracked ID (installed by a launcher that did not record actions) undoes every such action, as before. Backup-based actions keep relying on their backups. Every backup deletion deletes the records too: `Delete(InstallBackupId)` deletes the ID's records and those of the IDs it contains (path prefix with a separator, not `LIKE`), and `DeleteAll` (modpack uninstall and installation) deletes all of them.
- `mergePlugins` (`DownloadInfo` of a `plugins.txt`, named uniquely like any feed download; it replaced `reorderPlugins` and its `ExpectedOrder` list, which no published `feedV11.json` used) downloads the file and `ModOrganizerService.MergePlugins` merges it into the selected profile's `plugins.txt` through `PluginListMerger`. In a `CanRollback` step the profile, its `plugins.txt` before the merge and the merged file are backed up first (an existing backup is kept), and the rollback (`ModOrganizerService.RevertPluginsMerge`, `PluginListMerger.RevertMerge`) works on that profile, not the selected one: every plugin the merge did not list is taken from the current list with its current state, in its current order, which the rollback never changes, so plugins added, enabled or reordered since stay as they are, and plugins removed since stay removed. The merged plugins get back their previous state and relative order (those the merge added are removed), each going right after the last current plugin that the merge did not list and that preceded it in the previous list (first when there is none), so the plugins that preceded it before the merge, such as its masters, still do; with nothing changed since, the result is the previous list, since the merge moves only the plugins it lists. The file may list only some plugins (`*` marks an active one, `#` lines are comments); a plugin listed twice fails the action. Its plugins end up in its relative order and with its state, keeping the profile's letter case of a listed name; the plugins it does not list keep their places. The largest set of its plugins already listed in the right relative order stays (of equal sets, the plugins listed later, so the others move later, after masters they may have in between), and every other plugin, moved or new, goes right after the plugin preceding it in the file (the leading ones before the first staying plugin, or at the end when none stays). Then `loadorder.txt` is rebuilt (after a merge and its rollback alike) as its comments, the plugins it lists that neither the new nor the replaced `plugins.txt` lists (the primary plugins, kept first; a plugin the rollback removed is therefore dropped) and the plugins of `plugins.txt` in order, which is the layout Mod Organizer writes. `make_mocks.py` serves the real `plugins.txt` files of the mocked mods' `mergePlugins` actions.
- A modpack patch (`ModpackPatchFeedItem`) downloads its archive, extracts it into the Skyrim directory except the modpack version file (`LauncherProductOptions.ModpackVersionFile`, where `ModpackVersionProvider` reads the installed version), runs its optional `InstallSteps` (missing in the feed when there are none) in order, e.g. a `removeFileSystemItem` for files the patch makes obsolete, and only then extracts the version file (`ISevenZipService.ExtractArchiveExcept`, then `ExtractEntriesFromArchive` when the archive contains it). A patch whose steps failed or were interrupted therefore keeps the previous modpack version, so after a restart it is offered again and its steps are retried; steps must be safe to repeat. A patch is never rolled back, so `CanRollback` has no effect and the feed editor hides its switch for patch steps (showing it only to turn off a step loaded with it). Patches had a `PathsToDelete` list deleted before extraction, skipping paths that could not be deleted, until `feedV11.json` replaced it with these steps; the migrated steps set `FailOnFailedDelete: false` to keep skipping them, and feed patches never contain a path they delete, so the order change does not matter for them.
- Optional mods and graph packs are both installed by `InstallAppTaskProvider.CreateModInstallAppTask` from a `ModFeedData`: each version (`ModFeedItem`) has a required archive `ArchiveDownloadInfo`, which is downloaded and installed as the mod `Name` first, and optional declarative `InstallStep`s (missing in the feed when there are none) that run after it, in order. The version's and the `installMod` action's optional `Placement` (`ModPlacement`, a feed closed hierarchy) sets where the mod goes in the selected profile's `modlist.txt`, either under a separator or next to a mod, never both; without it a new mod gets Mod Organizer's default place (the end of the list). `ModOrganizerService.PlaceMod` applies it after the files are installed and before activation, keeping the mod's state. Mod Organizer shows the file bottom-up, so: `UnderSeparator` names a separator as shown, without the `_separator` suffix of its `mods` directory (the editor's `FeedRules.Separator` rejects the suffix and characters invalid in Windows file names), and moves the mod to the end of its group (right after the previous separator's line), creating a missing separator (directory, `meta.ini` and line) shown right above the consumer's `LauncherProductOptions.UserModsSeparator` separator, so the user's own mods stay last (at the end of the list when that separator is missing); `NextToMod` puts the mod directly `Below` (the line before, higher priority) or `Above` (the line after) the named mod, and leaves the list unchanged with a logged warning when that mod is not listed. Separators are never removed. The editor edits placements with `ModPlacementEditor` ("Размещение в Mod Organizer": default, separator, or mod) and `ModPlacementJsonConverter`. Actions that need an archive download it themselves: `installMod` names another mod (`DownloadInfo` and `ModName`) and downloads and installs it (the editor's `FeedValidator` rejects one naming the mod itself), and `extractArchive` (`DownloadInfo` and `DestinationPath`, relative to the Skyrim directory, empty for the Skyrim directory itself) downloads its archive and extracts it whole there. There is no download-only action. The feed keeps graph packs in their own `GraphPacks` list (order is the display and choice order). `GraphPackFeedData` derives from `ModFeedData` (and the editor's `GraphPackModel` from `ModModel`, edited by `GraphPackEditor` through `ModEditor`), so a graph pack is written exactly like an optional mod (`Name`, optional `DisplayName`, logo, description, `ModFeedItem` versions) plus `Recommendation`, optional `IsDefault` and optional `IsDiscontinued`; it is passed to `InstallAppTaskProvider` as is, and `GraphPacksView` shows them as `ModCardView` cards. A graph pack none of whose versions supports the installed modpack is shown disabled with the "Проходит обновление" tooltip, unless it `IsDiscontinued` (no new versions will be released): `GraphPackFeedData.IsOfferedFor` then hides its card (also when modpack is not installed) and leaves it out of the modpack installation, so old modpack versions can still install a removed graph pack while new ones do not show it. Only one graph pack can be installed: while any graph pack of the feed (hidden ones included) is installed or its install command is running, `GraphPacksViewModel` disables the other cards' install commands, and the card tooltip (`ModCardViewModel.UnavailableReason`, supplied by the card's owner and falling back to "Проходит обновление") names that graph pack; the installed graph pack is re-read after each graph pack install/uninstall and when the modpack installation state changes. All graph pack cards are also disabled while any task of the modpack installation chain is queued (`AppTaskProvider.IsModpackInstallationTask`: component choice, modpack, patches, English voices, graph pack), not just `InstallModpack`, because the chain installs its chosen graph pack in its last task after `InstallModpack` has replaced Mod Organizer; failed chain tasks keep the cards disabled until they are resumed or cancelled. A new task in the chain must get an ID that `IsModpackInstallationTask` recognizes. The list may be empty or missing (the editor omits it when empty), or every graph pack may be hidden: `HomeView` then hides the graph packs section and the modpack installation has no graph pack step or task. A graph pack has no install logic of its own: its archives and steps come entirely from the feed, and an update reinstalls it fully like an optional mod (rolls back the installed version's steps, removes the mod, installs the new version). The former `Part1DownloadInfo`/`Part2DownloadInfo`/`ProfileName` shape, whose steps the launcher built at runtime, was migrated in `feedV11.json` into the equivalent explicit steps. Graph pack versions set `SupportsUninstall` in the feed like any mod. The feed editor's `FeedValidator` checks a graph pack like a mod plus its `Recommendation`, and rejects duplicate graph pack names and more than one `IsDefault` graph pack that is not discontinued (a discontinued default applies only to the old modpack versions it supports). Do not add graph-pack-specific microtasks or install logic.
- Installed optional mods and graph packs are updated by reinstalling and uninstalled by rolling back: `CreateModInstallAppTask` first rolls back the installed version's feed item, then installs the new version, and `CreateModUninstallAppTask` only rolls it back (a mod that is not installed has nothing to roll back; an installed version the feed does not list has only its mod directory removed). Uninstalling is offered only for a feed version marked with the optional `ModFeedItem.SupportsUninstall` (`false` when missing, edited per mod version in the feed editor as "Можно удалить"), because the rollback does not undo the `removeFileSystemItem`/`extractArchive`/`mergePlugins` actions of a version installed by a launcher that took no backups, or for an installed version the feed does not list; running the uninstall task for a listed version without the flag throws. The rollback walks the `CanRollback` steps in reverse order, their actions reversed too, and then uninstalls the mod itself (`ModOrganizerService.UninstallMod`): `installMod` -> uninstalls the mod it installed (skipped with a warning when that mod is not installed, e.g. its conditional step did not run), `activateMods`/`activatePlugins` -> the same mods/plugins get the opposite state (a mod that is no longer installed is skipped with a warning, since it has no state to restore), `changeProfile` -> back to the modpack profile `LauncherProductOptions.ModpackProfileName` (the consumer-supplied profile selected by its archive), `removeFileSystemItem`/`extractArchive` -> restored from the action's backup, `mergePlugins` -> reverted from its backup keeping the plugin list changes made since (see the backups above); `selectRequiredMod` has nothing to undo. The installed version is always read from the mod's `meta.ini` (`1.0.0` when missing), which the launcher writes after installing a version or patch. `feedV11.json` dropped the mod's `VersionProvider` (`MetaIni` or `FileContent`, a version file in the mod directory) before it was published. `IInstallAppTaskProvider.GetModInstallState` returns a `ModInstallState` value: `IsInstalled`, `IsUpdateAvailable` (only when the installed version is listed in the feed and a newer feed version supports the installed modpack; an unlisted version cannot be rolled back by the feed's steps, so it is not updatable), and `IsUninstallSupported`. `ModCardViewModel` takes this state plus install and uninstall commands, which never run together: its install command then runs the update, and `ModCardView` shows "Обновить" instead of the disabled "Установлен" plus an accent dot in the card's top-right corner; when uninstalling is supported the card gets a third "Удалить" hover button (the `withUninstall` class moves the hidden panel further down to fit it). Graph pack confirmations do not depend on the steps: a first installation and uninstalling warn that saves need a new game, and an update (a full reinstall) asks nothing.
- Mod patches: a mod version (`ModFeedItem`, so graph packs too) may list optional `Patches` (`ModPatchFeedItem`: `Version`, `DownloadInfo`, optional `InstallSteps`; missing in the feed when there are none). A patch archive is extracted whole into the mod directory (`<ModOrganizerDirectoryName>\mods\<Name>`), then its steps run, and `meta.ini` gets the patch version after each patch's steps (and the version itself after the archive and steps), so an interrupted update leaves the last applied version and a patch whose steps failed is offered again. The `meta.ini` microtask resolves the stored path of the mod archive when it runs (after the download), and `ModOrganizerService.CreateOrUpdateMetaIniFile` keeps the recorded `installationFile` when the archive is no longer stored (e.g. a patch-only update after the downloads cleanup). Installing a version installs it and then all its patches in version order. `ModFeedData.FindItem` finds the installed version among versions and patches; when `CreateModInstallAppTask` targets the version the installed one belongs to and some of its patches are missing, only those patches are applied (no rollback or reinstall); a newer version reinstalls as usual. `GetModInstallState` offers an update while any version supporting the modpack has a later version than the installed one, including its patches (`ModFeedItem.GetLatestVersion`, a method so the source-generated serializer does not write it). Uninstalling or updating rolls back the `CanRollback` steps of the applied patches (`ModFeedItem.GetAppliedPatches`: patches up to the installed version), newest patch first, then the version's own `CanRollback` steps, then removes the mod; the editor shows the rollback switch for patch steps. `ModFeedItem.GetDownloads` includes the patches' archives. The editor edits patches per mod version in `ModItemEditor` ("Патчи", newest first like modpack patches); `FeedValidator` requires each patch version above its mod version and below the mod's next version, rejects a patch version equal to any version of the mod ("уже указана как версия мода", either direction) and duplicate patch versions within the mod.
- Modpack installation (`AppTaskProvider.CreateInstallModpackTask`, also used by `CreateRunGameTask`) shares one `ModpackComponentsSelection` across its task chain. The feed declares `InstallComponents` with stable IDs, graph-pack choice or mod-reference kind, localized title/description, supported modpack version range and chain order. Supported components are offered for the version reached after all patches, ordered by `Order`; mod references use the newest supported mod version. `SelectModpackComponents` is the installation's first dependency, before Skyrim/prerequisites. `SelectModpackComponentsMicroTask` fetches distinct download sizes only when showing the choices; `ModpackComponentChoices.Apply` records accepted tasks by component ID. After the main modpack and its patches, `InstallModpackComponent_{id}` tasks execute in feed order. Declined tasks become `IsUnneeded` immediately after the selection. Component ordering and mod names come entirely from the consumer feed; neither a voices mod name nor graph-pack version threshold is hardcoded in runtime code. `IsModpackInstallationTask` recognizes the component task prefix as well as the main install, patch, selection and removal tasks.
- Launcher updates: `UpdateProvider.GetLauncherUpdateInfo` returns a `LauncherUpdateInfo` when the feed has a launcher newer than the running one. The update installs the newest version, and `SupportsNewModpackVersions` is set when any launcher feed item newer than the running version (up to and including the newest, so a flagged intermediate release counts even though it is skipped) has `LauncherFeedItem.SupportsNewModpackVersions`, the marker of a release that is needed to install/update new modpack versions; `HomeView` then adds a line saying the update is needed for new modpack versions. The flag is optional in the feed (`false` when missing) and is edited per launcher in the feed editor.
- Byte sizes and speeds shown anywhere in the launcher, in Core-built texts and `LauncherKit.Desktop.Avalonia` converters (`BytesToStringConverter`, `BytesConverter`, `ExceptionDisplayConverter`) alike, go through `LauncherKit.Core.Utils.BytesFormatter`, so every surface uses the same binary units and format (e.g. "1.50 GB"). Do not add another byte formatter.
- `PrerequisitesAppTaskProvider` creates the VC++ redistributable and 7-Zip tasks. Both `AppTaskProvider` and `InstallAppTaskProvider` depend on it; `AppTaskProvider` depends on `InstallAppTaskProvider`, never the reverse.
- User choices during a task go through the generic `LauncherKit.Core.Choices` model: a microtask emits `MicroTaskStep.SelectChoices` with a `ChoiceSelectionContext` of `ChoiceStep`/`ChoiceOption` values, `AppTaskView` opens the choice dialog as soon as that step arrives (no extra click; the dialog has no cancel button, it closes only after the last step or when the microtask moves on) and shows them through `ChoiceSelectionViewModel`/`ChoiceStepViewModel`, and the context completes with one `ChoiceStepSelection` per step. Steps and options are compared by reference, so the producer maps the selection back to its own domain: FOMOD does this with `FomodChoices`, which turns `InstallStep`s into choice steps and the selection into `ConfiguredInstallStep`s; the feed `selectRequiredMod` action (`SelectRequiredModMicroTask`) asks for one installed required mod through a single `ExactlyOne` step. Do not add feature-specific selection dialogs.
- A `ChoiceOption` with a non-null `UnavailableReason` is unavailable: it is shown disabled with the reason, is never selected (its `IsSelectedByDefault` is ignored), and `ChoiceSelectionMode.All` counts only available options. An option cannot be both `IsRequired` and unavailable; `ChoiceOption` throws `ArgumentException` for that combination and for a blank reason. `FomodChoices` maps a FOMOD option with the static type `NotUsable` to an unavailable option, so the user cannot select it and its files are never installed.
- Downloads are written into `<name>.part` inside the downloads directory and are published under their final name only by `FileStorageService.Complete`, once every part is written. A file at the final path therefore means either a finished download or a copy the user placed there; the latter is adopted only after `Rehash` confirms its hash. Progress lives in the `FileParts` rows, never in the on-disk length, so `FileSourceDownloader` can download parts concurrently in any order.
- `FileStorageService.Allocate` reserves the whole file up front, so it is the only place that checks free disk space: the reservation itself removes those bytes from the reported free space, and checking again afterwards would demand a second copy's worth of space. A source that reports no byte-range support (`IFileSource.IsOffsetSupported`) gets exactly one part and is requested without a `Range` header; an interrupted download from such a source cannot resume and `DownloadFileMicroTask` re-allocates it from zero.
- Every `FilePart` row carries `LastWriteAt`, set when the part is allocated and on each flush of written bytes. `IFileStorageService.GetFileInfos` returns `StoredFileInfo` (not the DB model) for finished and partial files alike: `Status` is `Complete`/`Partial` and `LastWriteAt` is `FinishedAt` for a finished file or the latest part write for a partial one. `CleanupOldDataInitializer` deletes a file once its `LastWriteAt` is older than `DownloadSettings.FileStoragePeriod` (finished) or `PartialFileStoragePeriod` (partial). The Downloads page lists both with a status column.
- `IFileStorageService.Delete` returns `IFileStorageService.DeleteResult` instead of suppressing disk errors: `Deleted` (also for an unknown file), `FileInUse` (sharing/lock violation, e.g. a `.part` held open by a running download), `AccessDenied`, or `Error` with the exception. On failure the DB records are kept, so the file stays listed and the deletion can be retried; the Downloads page shows the reasons, and internal callers that cannot proceed without the deletion throw. The storage result unions (`GetOrCreateResult`, `RehashResult`, `DeleteResult`) are nested in `IFileStorageService`.
- Persistence uses two SQLite contexts (`SqliteDbContext`, Microsoft.Data.Sqlite): `GlobalDbContext` stores launcher-wide data in `launcher.db` (`LauncherConstants.GlobalDatabaseFileName`) in the launchers root; `SkyrimLocalDbContext` stores installation-local data in `<LocalDatabaseFileName>`. Each is scoped and owns one unpooled connection, opened on first use with `PRAGMA journal_mode=PERSIST` and closed with the scope; a connection is not thread-safe, so concurrent users of one context serialize their calls (as `OpenedFile` does with its lock). Queries are hand-written SQL run through the context's internal `Execute`/`Read` helpers with bound `$name` parameters, never interpolated values. Column formats are fixed by existing databases: `DateTimeOffset` is Unix seconds (`INTEGER`), `Sha256Hash` is upper-case hex text. `DbMigrator<TContext>` applies explicit migrations tracked in `__Migrations`, all pending ones in one transaction (every command in it must reference the transaction).
- Base endpoints are configured under the keyed `Urls` section. `UrlResolver.PreferredServer` picks the server `GetUri(key)` resolves to, and `GetUri(key, server)` resolves an explicit one; `FeedUtils` only appends feed-relative paths. Use `UrlKeys` rather than string literals for known endpoints. The preferred server is not persisted: it lives only in the singleton `UrlResolver`, starts as `DownloadServer.Main` on each launcher run, and is changed only by the download fallback, so `IUrlResolver` must stay a singleton.
- Feed downloads (the feed itself, `DownloadFileMicroTask` for feed `DownloadInfo`s, component sizes in `SelectModpackComponentsMicroTask`, the availability check) and analytics reporting go through `IDownloadServerFallback.Execute` (a singleton, like `IUrlResolver`): the operation runs on the preferred server and, when it fails because of the server (`HttpRequestException`, `HttpIOException`, `TimeoutException` including `DownloadStalledException`, Polly `TimeoutRejectedException`, or a cancellation the caller did not request), once more on the other server. Other failures (e.g. `NotEnoughSpaceException`) propagate without a second attempt. When the other server succeeds it becomes `IUrlResolver.PreferredServer` for the rest of the run. When both fail it throws `DownloadServersUnavailableException`, which `ExceptionDisplayConverter` shows to the user. `DownloadFileMicroTask` counts a download that receives no data for `StallTimeout` (15 s, measured from the start of the transfer, not while preparing the destination) as failed with `DownloadStalledException`; a paused download is not a failure. Plain-URL downloads (`DownloadFileSource.Http`) have no fallback. UI images and markdown use `IFeedUtils.GetUri(path)`, i.e. the preferred server, without fallback.
- `FeedProvider` is a singleton and caches the feed itself: one load runs at a time and every caller shares it. The load runs without any caller's cancellation token (a cancelled caller only stops waiting) and is cancelled only when the provider is disposed, which then throws instead of returning the default feed. A loaded feed is served for `FeedLifetime` (1 minute); a failed load returns the empty default feed (logged) for `FailedFeedLifetime` (15 s), so the next page visit after that retries. Each network load raises `FeedLoadEvent.Started` then `Succeeded` or `Failed(exception)` on `IFeedProvider.LoadEvents` (on the loading thread); cached reads raise nothing.
- On each launcher start, `InstallationAnalyticsInitializer` sends the persistent installation GUID and launcher version through `InstallationAnalyticsService` to the Analytics Worker. The report posts to the `Analytics` key's URL for the server chosen by `IDownloadServerFallback`, so it starts with the preferred server, retries on the other one after a server failure, and can switch the preferred server for the run. The initializer's 5 s timeout covers both attempts, so a hanging first server gets no second attempt. The Worker HMACs the GUID before writing it as Analytics Engine `index1`; reporting failures are logged but never prevent startup.
- OAuth is the generic part shared by integrations (`Core/OAuth/`): `Duende.IdentityModel.OidcClient` runs the authorization code flow with PKCE as a public client (no client secret ships in the launcher), `LoopbackBrowser` is its `IBrowser` (listens on the `http://127.0.0.1:{port}` redirect URI before opening the authorization page through `IExternalBrowser`, answers other paths such as `/favicon.ico` with 404, returns the first request to the redirect path, `Timeout` after `BrowserOptions.Timeout`), and `IOAuthTokenStore` keeps each provider's tokens in the global key-value storage (`OAuthToken_{provider}`) encrypted with DPAPI for the current Windows user. `IExternalBrowser` is implemented in `LauncherKit.Desktop.Avalonia` (`ExternalBrowser`, through `TopLevel.Launcher`). A new OAuth integration adds its own `OidcClient` wrapper and account service rather than another browser or token store. OidcClient requires the `openid` scope; the ID token comes from the token endpoint over TLS, so its signature is not checked (`RequireIdentityTokenSignature = false`).
- Discord: the user links an account with `IDiscordAccountService.Link`, which authorizes the `Discord:ClientId` application (it must be a public client with `http://127.0.0.1:{Discord:RedirectPort}/discord/callback` registered) with the scopes `openid identify guilds.members.read`, then reads the user (`GET /users/@me`: ID, user name, display name, avatar, falling back to Discord's default avatar) and the membership in the `Discord:GuildId` server (`GET /users/@me/guilds/{id}/member`: nickname, server avatar, and role IDs; 404 means not a member) through `DiscordApiClient` and stores the tokens only once both succeed. Role IDs never change, so features compare them with known IDs; role names would need a bot token, which the launcher cannot ship. `GetLinkedAccount` re-reads the account on every call (the settings page reads it when shown), refreshing tokens that expire within a minute under a lock, since Discord rotates the refresh token; a rejected refresh token (`invalid_grant`), a 401 from the API, or tokens that cannot be decrypted forget the link and return `null`, while network failures throw and keep it. `Unlink` forgets the tokens first and then revokes both of them, only logging a failed revocation (an error response or a timed-out request; only a cancellation by the caller propagates). `DiscordSettings` are validated when first used, so a missing client or server ID fails linking with the validation message instead of failing startup. The launcher reaches `discord.com` directly (no proxy), so users where Discord is blocked need their own VPN.
- `GetCachedLinkedAccount` serves the last read for `AccountCacheLifetime` (5 minutes) and a failed read for `FailedReadCacheLifetime` (1 minute, rethrowing it), for frequent readers such as feed filtering; `GetLinkedAccount`, `Link`, `Unlink` and forgetting a rejected link update the cache, and the last three raise `IDiscordAccountService.LinkedAccountChanged`.
- Beta access: `FeedProvider.GetModpackFeedItems` always offers releases; a prerelease modpack feed item is offered only when an activated beta code's `BetaVersions` range (hashed beta code -> modpack version range) covers it, when the linked Discord account (through `GetCachedLinkedAccount`) has any role of the optional feed list `FeedData.DeveloperRoleIds` (modpack developers get every prerelease), or when the item has the optional `ModpackFeedItem.IsAvailableForSponsors` (`false` when missing) and the account has any role of the optional feed list `FeedData.SponsorRoleIds` (role IDs on the `Discord:GuildId` server, written as JSON strings). A prerelease no beta code covers is therefore hidden from everyone else. Discord is asked at most once per call and only when a hidden prerelease could be unlocked (a sponsor item, or any hidden prerelease when developer roles are listed); a failed read is logged and hides those items instead of failing the feed. Launchers that predate role access show a prerelease no beta code covers to everyone (this was accepted rather than bumping the feed file name, so such a prerelease leaks to users of those launchers). The feed editor's `FeedValidator` accepts `IsAvailableForSponsors` only on a prerelease, requires at least one sponsor role when any item is marked, and checks both role lists for duplicates and invalid snowflakes. `IFeedProvider.BetaAccessChanged` fires when a beta code is activated or `LinkedAccountChanged` fires, and `HomeViewModel` then reloads the update info. The Discord settings card reads `IFeedProvider.GetBetaAccessRoles` and mentions the developer role (all beta versions) or else the sponsor role only when it was found; otherwise it shows server membership. The editor edits both role lists on the "Бета-доступ" tab and the sponsor flag per modpack release ("Доступна спонсорам").
- `LauncherKit.FeedEditor` edits one feed (`R2:FeedKey`, STB: `feedV11.json`). Each user signs in with their own R2 credentials, kept only in the scoped Blazor circuit's server memory. Saving uses ETag/`If-Match` with an overwrite-conflict dialog, and reload/discard and leaving the page ask before discarding unsaved changes. The mutable feed models use Modpack names, a required `DefaultLanguage`, side-by-side language maps for all localized text/Markdown paths, install components (kind, mod reference, supported range, numeric chain order) and prerequisites (download and arguments). Nullable localized fields are omitted only when null; any supplied map must contain its exact default-language key and nonblank translations. The editor does not reference Core: versions/ranges remain validated text, closed install-action/placement hierarchies use hand-written `$type` converters, and unknown properties survive round-trips. Keep `FeedJsonTests` and the `feedV11.json` fixture compatible with Core's `SourceGeneratedJsonContext`.
- Feed paths that name bucket objects (download `S3Path`s, logo/description/changelog paths) are relative to the bucket root. With the feed, `FeedSession` lists every key in the bucket into `ObjectKeys` (skipping `/`-terminated folder markers); `S3PathField` offers them as autocomplete suggestions while still accepting any text. "Обновить пути" (refresh paths) re-lists after uploads without discarding edits. Paths relative to the Skyrim or mod directory stay plain text fields. A failed listing fails sign-in/reload with a `FeedStorageException`, so the R2 token also needs list access.
- When a non-empty `S3PathField` path is not in `ObjectKeys`, the field offers "Загрузить файл": the browser sends the chosen file under that exact key straight to R2 through presigned URLs, so it passes through neither the server nor the Blazor circuit. `FeedSession.StartUploadAsync` returns an `ObjectUpload`: up to `FeedSession.UploadPartSize` (64 MiB) a single `PUT` (its URL signs the file's content type, which the browser must send as is), larger files a multipart upload of equal 64 MiB parts plus a shorter last one (R2 requires equal parts and limits single requests). `S3PathField` sends up to 4 parts at a time, asking `GetUploadPartUrlAsync` for each part's URL (valid 1 hour) just before sending it; the browser side is `wwwroot/js/upload.js` (XHR, for upload progress). `CompleteUploadAsync` completes the multipart upload with the parts' ETags and adds the key to `ObjectKeys`; the first failed part, unreadable file, or cancellation (button or leaving the field) stops the other requests, and `AbortUploadAsync` makes R2 discard the parts. The upload replaces an object created under the same key meanwhile, and the R2 token needs write access.
- Direct uploads need CORS rules on the bucket (the editor's token cannot set them): allow each origin the editor is opened from (e.g. `http://127.0.0.1:8080` for Docker) to `PUT` with the `Content-Type` header, and expose the `ETag` response header, which multipart completion needs (`CompleteUploadAsync` fails with a message naming CORS when it is missing). Since no file passes through the circuit, it keeps Blazor's default message size and WebSocket compression (which also makes Blazor send its `frame-ancestors 'self'` CSP).
- While the parts are sent, a Web Worker (`wwwroot/js/sha256-worker.js`) reads the file again in 8 MiB chunks and hashes it with hash-wasm (vendored as `wwwroot/lib/hash-wasm/sha256.umd.min.js` with its MIT license; Web Crypto cannot hash a multi-gigabyte file incrementally). The SHA-256 (uppercase hex, the form feed hashes use) goes to the field's `OnSha256Known` callback; `DownloadInfoEditor` uses it to replace the download's `Hash`, since the uploaded file replaces whatever the path pointed to. When hashing is slower than the upload, the progress line shows the hashing progress after the upload reaches 100%.
- Choosing an existing key in an `S3PathField` with `OnSha256Known` set (only `DownloadInfoEditor`'s) reads the object's metadata (`FeedSession.GetObjectSha256Async`, a `HeadObject`): when it has `x-amz-meta-checksum-sha256` user metadata holding a hex SHA-256, the field reports it uppercased through the same callback, so the download's `Hash` is replaced. Objects without it, a malformed value, or a failed request (logged) leave `Hash` unchanged. R2's own `x-amz-checksum-sha256` is not used: R2 keeps it only for single `PutObject` uploads that sent it, and for multipart uploads only a checksum of the parts.
- The feed editor UI is in Russian: component texts, `ModInstallActionDisplay` names, `FeedRules`/`FeedValidator` messages and locations, and `FeedStorageException` messages are written in Russian directly (no resource files). Log messages and internal exceptions (`InvalidOperationException`/`ArgumentException`) stay in English. List-item factory labels are accusative nouns because `ListEditor` renders them as "Добавить {label}".
- `ListEditor` adds new entries at the start and puts a copy ("Дублировать") above its original, since most feed lists are newest-first. Lists ordered by position rather than age set `AddToEnd`, which adds at the end and puts copies below the original: graph packs and mods (the launcher shows them in list order), mod install steps (conditions refer to steps by number), and step actions.
- Optional sections of an entry ("Дополнительные шаги установки" and "Патчи" of mod versions, mod patches, modpack releases and modpack patches) are `ExpanderSection`s: compact outlined boxes (not MudBlazor expansion panels, whose collapsed headers are tall and unseparated), collapsed by default, rendered only while expanded, with the entry count in the title.

## Code Conventions & Common Patterns

- Follow `.editorconfig`: tabs, width 4; YAML uses two spaces, Python four spaces; trim trailing whitespace.
- Nullable reference types and implicit usings are enabled. C# uses `LangVersion=preview`; warnings and enabled analyzers must remain clean.
- Use standard C# naming: PascalCase types/members, `I`-prefixed interfaces, and clear service/provider suffixes such as `FeedProvider`, `ModOrganizerService`, and `AppTaskQueue`.
- UI follows MVVM. Prefer compiled XAML bindings, CommunityToolkit.Mvvm `[ObservableProperty]`/`[RelayCommand]`, `ViewLocator`, and the existing `WhenActivated` lifecycle pattern. Do not put install/update logic in code-behind.
- A boolean property (`IsVisible`, `IsEnabled`, ...) bound to whether an object is null or not must use `Converter={x:Static ObjectConverters.IsNull}` or `ObjectConverters.IsNotNull`, never `!`/`!!`. Avalonia's `!` converts with `Convert.ToBoolean`, which fails for a non-null object that is not `IConvertible` (e.g. `NuGetVersion`); the failed binding leaves the property at its default (`IsVisible` stays `true`), so `!obj` never hides the element, and `!!obj` is right only because two errors cancel out.
- Register dependencies in the existing `ServiceCollectionExtensions` composition methods and inject interfaces through constructors. Do not add service locators or parallel composition mechanisms.
- Preserve the event-driven model: R3 observables carry state/progress changes; app work is represented as dependency-aware `AppTask` graphs rather than ad hoc background work.
- Async service methods pass `CancellationToken` through download, process, archive, and task boundaries. Preserve cancellation; do not replace async I/O with blocking calls.
- Log operational failures with the existing `ILogger`/Serilog patterns. Throw `InvalidOperationException` or `ArgumentException` for broken invariants/invalid inputs; do not silently recover from corrupt state. Serilog object capturing is switched off for NativeAOT (`Serilog.Capturing.IsStructureValueSupported=false` in the consumer executable project), so `{@x}` logs `x.ToString()`; log the needed properties as separate placeholders instead.
- Persistence changes require hand-written SQL through the context helpers plus an explicit migration for the appropriate context; existing databases must keep working, so never change how an existing column is stored. Keep global and Skyrim-local state separated.
- Closed sets of in-process results, events and states are C# 15 `union` types whose cases are nested `sealed record`s (field-less cases are plain `sealed record Case;` and are used as `Case.Instance`). Consume them with exhaustive switch expressions (switch statements and `if` chains are not checked for missing cases); for side effects, switch to an `Action` and invoke it. A union's `ToString()` is its type name, so never interpolate or log a union directly (log `.Value`, or map the case to text). Do not serialize unions.
- Shared stateless instances (union cases, comparers, null objects) are `T.Instance`, the static extension property from `LauncherKit.Infrastructure.SingletonExtensions` (backed by `SimpleSingleton<T>.Value`) available on any class with a public parameterless constructor; do not declare a per-class `static Instance` member. The exception is value converters referenced from XAML through `{x:Static ...Converter.Instance}`, because `x:Static` resolves only members declared on the type.
- Feed types with cases (`InstallAction`, `ModPlacement` in `feedV11.json`) are `[JsonPolymorphic(InferClosedTypePolymorphism = true)] public closed record` hierarchies with public nested `sealed record` cases, one level deep, consumed with switch expressions over the case types. They are written as `{"$type":"CaseName", ...case properties...}` only through `SourceGeneratedJsonContext` (no custom converters); `$type` must be the first property, and an unknown, missing or non-first `$type` fails the feed load. The case type name is the discriminator, so renaming or removing a case is a breaking feed change (bump the feed file); adding an optional property is not. Case-less choices (`CompareOperator`) are plain enums written as strings.
- Maintain NativeAOT compatibility; a consumer's publish fails on any trim/AOT warning (see "Consumer SDK and NativeAOT requirements"). Use source-generated alternatives instead of reflection (`SourceGeneratedJsonContext`, the configuration binding generator enabled in Core, `[GeneratedComInterface]`/`[LibraryImport]` with `StrategyBasedComWrappers` for COM and P/Invoke, compiled bindings including `CompiledBinding.Create` in code, NetEscapades enum generators). Avoid: reflection over members chosen at run time (`Type.GetType`/`GetProperty`/`GetMethod` with non-constant names, `Activator.CreateInstance(Type)`), string `Binding` paths and reflection-bound controls (DataGrid default sorting: set `CustomSortComparer`), `Array.CreateInstance`/`MakeGenericType` over unknown types, built-in COM (`[ComImport]`), `dynamic`, Serilog `{@x}` destructuring, and `Assembly.Location` (empty in a single native exe; use `AppContext.BaseDirectory`). `ViewModelBase` is an `ObservableObject`; a view model that validates implements `INotifyDataErrorInfo` itself (as `DirectoryBrowserViewModel` does) instead of using `ObservableValidator` or validation attributes.
- Add external base URLs under `Urls:<key>` with both `MainUrl` and `ProxyUrl`, then resolve them through `UrlResolver`. Do not inject endpoint URLs directly into feature-specific settings or duplicate proxy-selection logic.
- Keep all analyzer warnings at zero. Do not suppress warnings unless the warning is demonstrably inapplicable and a narrow suppression includes a clear justification.
- Prefer clear framework and BCL APIs over custom wrappers.
- Prefer immutable values and explicit domain types when they protect a real invariant; avoid speculative layers, generic repositories, service locators, marker interfaces, and one-use abstractions.
- Avoid unnecessary allocations, repeated enumeration, blocking calls such as `.Result` or `.Wait()`, and broad exception catches.
- Use best practices for C#/.NET development, such as SOLID, etc.
- Use latest C# version.
- Favor unit-testable design: keep business logic in services/helpers and avoid static or UI-coupled logic when possible.
- Treat warnings as errors; fix analyzer issues instead of suppressing.
- Prefer `PascalCase` for types/methods and `camelCase` for locals/parameters.
- For enums, use the NetEscapades.EnumGenerators source-generated methods instead of reflection-based `Enum.*`.
- Third-party NuGet packages are allowed when they improve delivery; document new dependencies in PRs.
- Use read-only version of collection interfaces where possible (`IReadOnlyCollection<T>`, `IReadOnlyList<T>`, `IReadOnlyDictionary<TKey, TValue>`, etc.).
- For JSON deserialization, create POCOs with immutable properties and use `System.Text.Json`. Do not create unused properties.
- Avoid primitive obsession for types that are not simple value types (Emails, Symbols, etc.).


## Consumer SDK and NativeAOT requirements

- Use the .NET 11 SDK, including prerelease SDKs while needed (the consumer's `global.json`), and `LangVersion=preview`: public APIs use `union`, `closed record` and `extension` members. Desktop consumers target `net11.0-windows`; FeedEditor/FOMOD target `net11.0`. The NUKE host and build components target `net10.0`.
- Stay on the centrally pinned Avalonia **12.1.x** line in `Directory.Packages.props`. DevAutomation uses unstable/private Avalonia APIs, so a version change requires rechecking its accessors as well as normal UI/AOT acceptance.
- Consumers declaring their own observable properties use CommunityToolkit.Mvvm. Consumers binding their own options enable `EnableConfigurationBindingGenerator`; keep source-generated JSON, bindings and interop for NativeAOT.
- NativeAOT executable consumers require `UseOptimizedPublish=false` so SDK 11 includes Avalonia resources and compiled XAML. Keep the consumer's `CollapseCheckedThirdPartyTrimWarnings` target and its narrowly audited assembly list; warnings in all other assemblies remain errors. Re-audit collapsed dependencies on upgrades rather than broadly suppressing warnings. Warnings are errors, and ILC gets `--warnaserror` from `TreatWarningsAsErrors`; a `#pragma warning disable` hides a warning from Roslyn only, so fix the code (or use `[UnconditionalSuppressMessage]` with a justification when it is demonstrably safe).
- Preserve `MarkProjectSatelliteResourcesForAot` in `Directory.Build.props`: SDK 11 project-reference satellite outputs require `AssetType=resources` before `_ComputeIlcCompileInputs`. Losing this metadata silently drops kit translations from AOT executables.
- `Microsoft.Extensions.{Configuration,DependencyInjection,Logging}.Abstractions`, `Microsoft.Extensions.Options` and `Microsoft.Extensions.Primitives` are supplied by the .NET 11 shared framework; do not add redundant package references (NU1510).
- Distribution is source-only: consumers pin a commit of this repository as the `kit/` submodule, and kit changes reach them by updating that pointer. Consumers import `Directory.Build.props`/`Directory.Packages.props`, `msbuild/LauncherKit.Product.props` and `installer/` by path, so renaming or moving these files, `src/` projects or `installer/Bundle` breaks consumers. No NuGet packages are published; do not introduce package publication or package-reference switches without a distribution decision.
- A change to a consumer contract (product properties, `LauncherKitApp` hooks, required registrations, view model facts, installer properties, `LauncherBuild` members) needs the matching update in the reference consumer; describe it in the pull request.
- Local databases, settings overrides, logs, caches, downloads and generated `out/`, `bin/`, `obj/` are not source-of-truth fixtures.

## Unit-Testing Guidance

- Use NUnit and the packages already configured in `Directory.Packages.props`.
- Name tests after behavior and outcome, not implementation details.
- Tests must be deterministic, isolated, and safe to run in parallel. Do not depend on test order, wall-clock timing, random values, local developer state, or external network services.
- Test public behavior and observable contracts. Avoid tests that merely assert source structure, framework plumbing, or private implementation details.
- For defects, add a regression test that fails for the original bug and passes for the fix.
- Cover success, boundary conditions, invalid input, and meaningful error translation when they are part of the changed behavior.
- Prefer realistic endpoint/integration coverage for HTTP contracts and focused unit tests for domain logic. Mock only owned boundaries where a real dependency would make the test nondeterministic or impractical.
- Name test classes `*Tests` and methods `MethodName_Scenario_Expected`.
- Place unit test files under `tests/<Project>.Tests/`, mirroring the target class file location in `src/<Project>/`. Consumer code is tested in the consumer repository.
- Use AAA pattern.
- Use the new NUnit assert syntax.
- Use a strict version of `AutoMocker` (example: `var mocker = new AutoMocker(MockBehavior.Strict);`).
- Do not construct real implementations as dependencies of the class under test; resolve the target with `AutoMocker` (`mocker.CreateInstance<T>()`) and configure its mocks via `mocker.GetMock<TDependency>()`. Real types are acceptable only for plain value/option objects that carry no behavior, and for the database: a class that runs SQL through `GlobalDbContext` or `SkyrimLocalDbContext` gets a migrated context from `tests/LauncherKit.Core.Tests/TestSupport/SqliteDatabase.cs` through `mocker.Use(context)` (as `FileStorageServiceTests` and `InstallBackupServiceTests` do), since the contexts cannot be mocked and a fake would leave the SQL untested.
- Never write `new Mock<T>(...)`. Every mock must come from the test's `AutoMocker` via `mocker.GetMock<T>()`, so the mock is created with the mocker's strict behavior and is automatically injected into `mocker.CreateInstance<T>()`. Use `mocker.Use<T>(instance)` only for behaviorless infrastructure instances such as `NullLogger<T>.Instance` or a hand-written stub, and for the database contexts above.
- Shared test helpers must not create mocks on their own either: they take the `AutoMocker` as their first parameter and configure `mocker.GetMock<T>()` (see `tests/LauncherKit.TestSupport/OptionsStubs.cs` and `MockHttpClientFactory.cs`).
- Do not use class fields to store shared test data to allow multiple tests to run in parallel.
- Use `RichardSzalay.MockHttp` to mock HTTP requests.

## Testing & QA

- NUnit tests live under `tests/`, with one test project per production project plus `LauncherKit.TestSupport` for shared deterministic fixtures. `fomod-installer/` has its own tests and solution.
- There is no separate lint command: `dotnet build LauncherKit.sln -c Debug` is the static-analysis check (warnings are errors, latest analyzers enabled) and must succeed without any consumer files.
- Run `dotnet test LauncherKit.sln -c Debug` for the whole kit suite, or `dotnet test tests/<Project>.Tests -c Debug --filter FullyQualifiedName~<Fixture>` for a focused fixture.
- The consumer's NUKE `Test` target (`.\build.ps1 Test --configuration Debug`, inherited from `LauncherBuild`) runs kit and consumer tests together and writes TRX and coverage under the consumer's `out/test-results`. Coverage is reported but has no threshold until a stable baseline supports a ratchet.
- The analytics Worker has a committed Vitest suite. Worker changes require `npm ci`, `npx tsc` and `npm test -- --run` from `workers/analytics/` (the tests use the independent `test/wrangler.jsonc`); ingestion changes also require a local `npm run dev -- --config <consumer>/workers/analytics/wrangler.jsonc` smoke request with a consumer's Wrangler configuration.
- For launcher changes, build the kit solution, then exercise the changed flow in a consumer whose `kit/` submodule points at the change (see [dev automation](docs/dev-automation.md)). Publish/trim/AOT-sensitive changes also require the consumer's NUKE publish target (`.\build.ps1 PublishLauncher`), and UI changes should be exercised in the published AOT exe, not only in a JIT run. Installer changes require the consumer's `.\build.ps1 PublishInstaller` and an install/upgrade of the resulting setup.
